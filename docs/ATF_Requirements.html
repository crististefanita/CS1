3. Contracte funcționale obligatorii

ConfigurațieMUST
  • MUST toate setările să fie citite printr-un singur ConfigManager/provider;
  • MUST să existe require(key) pentru valori obligatorii și get(key, default) pentru valori opționale;
  • MUST base URL, auth, timeout, retry, report path și feature flags să fie configurabile fără recompilare;
  • MUST secretele să vină din environment/secret store/CI, niciodată din repository;
  • MUST NOT testele să citească direct variabile de sistem sau să modifice global clientul.
Separarea test / step / service / validatorMUST
  • Testul exprimă intenția de business: create_user_success, invalid_email_is_rejected.
  • Step-ul creează requestul prin factory, execută service-ul, înregistrează semantic requestul și returnează un rezultat utilizabil.
  • Service-ul definește operația și calea relativă; nu validează.
  • Validatorul primește response-ul și produce o eroare clară: expected, actual, path, body fragment, headers relevante.
  • Orice flow care creează date trebuie să declare cleanup, inclusiv la failure, skipped sau timeout.
Contractul de request/responseMUST
  • Requestul are metodă, path relativ, query, headers, body opțional, auth profile și timeout.
  • Response-ul păstrează status, headers, body raw, body JSON parse-uit, duration, attempt count și correlation id.
  • JSON-ul request/response se loghează pretty-printed, cu masking pentru token, cookie, authorization și câmpuri declarate sensibile.
  • URL-ul complet se derivă din baseUrl + relativePath; path-ul relativ rămâne vizibil în titlul pasului.
Reguli de eșec și continuitateMUST
  • O aserțiune eșuată marchează testul Failed, cu pasul și diagnosticul în Extent.
  • Un test negativ care obține răspunsul de eroare așteptat este Passed; „negative” descrie comportamentul verificat, nu rezultatul raportului.
  • Erorile în afara unui pas activ trebuie atașate la test-level și să închidă curat starea reporterului.
  • Cleanup-ul best-effort trebuie să fie vizibil ca eveniment controlat, nu să ascundă cauza originală.

5. Execuție HTTP și retry

Client și autentificarecomportament observat
  • Clientul inițializează o singură dată base URL-ul din config.
  • Requestul JSON setează Content-Type: application/json și Accept: application/json.
  • Requestul autentic adaugă Authorization: Bearer <token>; requestul explicit fără auth nu adaugă headerul.
  • Noua implementare trebuie să suporte profile de auth: bearer, basic, api-key, none, custom headers, cu secret masking.
auth:
  profiles:
    default:
      scheme: bearer
      token: ${API_TOKEN}
    anonymous:
      scheme: none
    invalid:
      scheme: bearer
      token: ${INVALID_API_TOKEN}
Policy 429 și Retry-Afterpăstrat, făcut configurabil

Implementarea actuală reîncearcă numai pentru statusul 429, cât timp bugetul de retry nu este epuizat. Delay-ul este citit din primul header nenul dintre Retry-After, variantele de casing și x-ratelimit-reset, este folosit ca număr de secunde, fallback-ul este configurat, iar valoarea este plafonată.

InputDecizieCerință .NET
status ≠ 429completează fără retryimplicit, dar policy extensibilă
429 + attempts disponibileretry + delaylog attempt și delay în pas
429 fără headerdelay defaulttelemetrie: fallback folosit
header invalid / ≤0delay defaultnu fail-ui retry logic
delay peste maxdelay cappednu aștepta necontrolat
retry budget epuizatreturnează ultimul responserezultatul final trebuie evaluat de assertion; nu marca automat functional PASS
Gap de păstrat în backlog: în Java, după epuizarea retry-urilor, ApiActions închide apelul cu pass("Call completed"); dacă testul nu are o validare explicită, un ultim 429 poate apărea ca apel trecut. În .NET, engine-ul trebuie să distingă „transport completed” de „business contract passed”.
Polling / eventual consistencynu este sleep arbitrar
  • Polling-ul primește o funcție care face requestul, o condiție și intervalul.
  • Timeout-ul vine din config (api.wait.timeout.seconds), nu este hardcodat în test.
  • Ultimul response este returnat dacă timeout-ul expiră; apoi validatorul produce diagnosticul final.
  • În .NET se recomandă CancellationToken, deadline monotonic și backoff configurabil, cu număr de încercări și duration total logate.
Model de rezultat al executoruluicontract recomandat
ApiExecutionResult
  response: ApiResponse
  attempts: int
  totalDurationMs: long
  retryEvents: [ { status, header, delayMs, reason } ]
  correlationId: string
  transportError: optional
  finalState: Completed | TransportFailed | Cancelled

Validatorii decid rezultatul funcțional; executorul decide doar rezultatul transportului și istoricul încercărilor.

Cerințe de calitate pentru aserțiuniMUST
  • Toate regulile care descriu același contract HTTP se acumulează într-un singur validation step; fiecare regulă este rând, nu child step separat.
  • Validatorul nu face network calls suplimentare decât dacă regula este explicit de tip eventual consistency/relationship.
  • Mesajul de eroare trebuie să includă regula, path-ul JSON/headerul, expected, actual și un fragment safe din response.
  • Validările din teste nu se implementează prin Assert dispersat dacă există validator echivalent; direct assertions sunt permise doar pentru meta-verificări locale.
  • Contractele compuse trebuie să poată fi serializate ca YAML și executate de un runner generic.

Semantica cerută: o operație HTTP este un step de execuție cu request/response; validările care îi verifică contractul sunt agregate imediat după aceea într-un singur step de tip Validate: <contract>.

Consecință de design: un contract cu 7 reguli produce un singur card de validare și o singură evidență tabelară cu 7 rânduri. Request JSON, response JSON și trace-ul tehnic rămân evidențe colapsabile ale step-ului HTTP/validation, nu devin pași concurenți care fragmentează triage-ul.

Criteriu de consistență: aceeași colecție de rânduri trebuie să poată fi produsă de validatorul C#, de un scenariu YAML/JSON și de un viitor adapter .NET fără schimbarea formatului Extent.
Trasabilitate către codul sursă pentru regula tabeluluiValidationEvidence

În implementarea analizată, Automation.Core.Validations.ValidationEvidence acumulează rânduri Name / Expected / Actual, iar AuditedPolicyApiReport.Validate(...) le publică o singură dată pentru contract. Noul ATF păstrează aceeași semnificație și adaugă explicit coloana RESULT.

7. Date, modele și cleanup

Date de testfixtures + generators
  • Fixture-urile statice sunt fișiere JSON încărcate printr-un provider de resurse.
  • Factories generează requesturi valide și variante mutate: email invalid, gender/status invalid, câmp lipsă, duplicate.
  • Generatorul trebuie să permită seed explicit pentru reproducere, dar să evite coliziuni între run-uri paralele; seed-ul de business și nonce-ul de run se loghează fără date secrete.
  • DTO-urile request/response sunt distincte; nu se reutilizează response ca request fără mapping controlat.
  • Fixture gap-ul trebuie să producă un status vizibil (Blocked/Expected failure), nu un test care pică aleator.
Modele minimecontract
UserRequest:  name, email, gender, status
UserResponse: id, name, email, gender, status
PostRequest:  title, body
CommentRequest: name, email, body
ApiErrorMessage: message
ApiValidationError: field -> messages[]

Pentru .NET, DTO-urile trebuie să aibă naming policy configurabilă (camelCase implicit), null handling explicit și validare separată de deserializare.

Cleanup și izolarea stăriiMUST
  • Testul înregistrează resource IDs create într-un cleanup registry per test invocation.
  • Cleanup-ul se execută în finally/AfterEach chiar dacă testul a eșuat.
  • Delete-ul de cleanup este marcat best-effort, dar se păstrează în report status, endpoint, id și excepția dacă apare.
  • Testele paralele nu împart user/post IDs sau obiecte mutable.
  • Cleanup-ul nu trebuie să șteargă resurse preexistente decât dacă sunt marcate explicit ca owned de test.

9. Reporting Extent-only

Decizie fixă pentru noul ATF: nu se include Allure, nu se expune un selector de engine și nu se păstrează listeneri/artefacte Allure. Extent este singurul backend de reporting.
Artefact unic, fără folder extentMUST — raport portabil

La finalul suitei se livrează un singur fișier HTML autonom, direct în artifacts/reports/ (timestamped sau nume explicit). Toate resursele Extent/Spark necesare — CSS, JavaScript, fonturi, iconuri și logo — sunt inline în acel HTML. Folderul auxiliar artifacts/reports/extent/ nu este permis: dacă reporterul îl creează temporar, adapterul trebuie să facă inline înainte de flush final și să-l șteargă înainte de a declara run-ul terminat.

  • HTML-ul nu trebuie să conțină referințe relative extent/... și nu trebuie să depindă de CDN.
  • Verificarea de acceptare enumeră recursiv artifacts/reports și acceptă doar raportul/rapoartele HTML și fișierele explicit aprobate de pipeline.
  • Raportul se poate deschide offline prin file: fără resurse lipsă, iar ștergerea folderului auxiliar nu schimbă randarea.

  • Reporterul nu schimbă verdictul funcțional și nu înghite excepția originală.
  • assertionTable(rows) este forma standard pentru validări agregate; tabelul este colapsat implicit, dar păstrează toate rândurile pentru triage.

Regula de afișare: schimb HTTP coerent, nu zgomot de evenimentedecizie UX obligatorie

Un API step trebuie citit de sus în jos ca o unitate: titlu METHOD + PATH, apoi evidența tehnică, body-ul requestului dacă există, evidența response-ului, body-ul response-ului și, în final, validarea contractului. Toate blocurile sunt colapsate inițial; primul click deschide doar pasul, iar fiecare sub-bloc rămâne controlabil independent.

JSON bodies — densitate vizuală cu 10% mai compactă și suprafață cu 20% mai deschisămai mult conținut vizibil, aceeași evidență

Body-urile JSON trebuie să fie mai subțiri vizual cu aproximativ 10% față de baseline-ul raportului actual, fără truncare și fără scroll orizontal. „Mai subțire” înseamnă densitate tipografică și spațiere redusă, nu eliminarea liniilor sau a indentării utile. Separat de densitate, suprafața code-block-ului JSON trebuie să fie cu aproximativ 20% mai deschisă decât dark-ul global, pentru ca payload-ul să fie scanabil fără a pierde tema dark.

10. Model configurabil de cerințe

Limită configurabilă pentru ACTUAL în assertion tablediagnostic compact, semantică neschimbată

Valoarea ACTUAL din tabelul unic ASSERTION / EXPECTED / ACTUAL / RESULT trebuie să aibă o limită configurabilă, nu un prag hardcodat în validator. Cheia este deținută de modul în modules.<moduleId>.config.reporting.assertionMaxDisplayCharacters (în implementarea .NET: ReportingSettings.AssertionMaxDisplayCharacters), este pozitivă și are default recomandat 240.

  • limita se aplică uniform tuturor validatorilor: status, header, body, JSONPath, relationship, schema și assertions configurate;
  • trunchierea este numai pentru prezentare; response/request raw și rezultatul folosit de assertion rămân complete;
  • textul scurt rămâne neschimbat, iar textul lung se termină explicit cu …;
  • limita este transmisă prin portul reporterului către tabelul agregat, astfel încât test doubles și adapterul Extent să observe același contract;
  • există unit/component tests pentru valoarea implicită, override configurat, valoare invalidă și păstrarea verdictului funcțional.

Configurația de mai jos este contractul propus pentru a putea recrea testele în .NET sau alt limbaj. Ea separă ce este variabil (URL, auth, resurse, scenarii, reguli) de ce este fix (semantica executorului, validatorilor și reportingului).

Regulă de ownership: configurația executabilă nu stă la rădăcina soluției și nu se păstrează într-un folder global config/. Fișierul comun de configurare se păstrează în Atf.Core/Configuration/appsettings.json, lângă loaderul comun; în interiorul lui, fiecare modul își deține propriul bloc modules.<moduleId>.config, inclusiv environment, execuție, reporting, auth, scheme, servicii, date și scenarii. Atf.Common nu deține fișiere de configurare, ci doar componente reutilizabile. Astfel, un ATF poate adăuga ulterior module precum billing sau claims fără coliziuni de configurare, iar runnerul poate încărca și valida un modul izolat.

Contractul tipizat al unei rutecerință pentru auth și raportare

Catalogul de rute trebuie să fie o clasă/registry centrală, analogă cu Routes.cs din framework-ul de referință, dar fiecare rută trebuie să transporte metadate executabile și tipizate, nu doar un path string.

ApiRoute
  name: users.create
  method: POST
  pathTemplate: /public/v2/users
  resource: users
  operation: create
  authentication:
    type: Bearer          # enum; nu text liber în catalog
    requirement: Required # enum; Optional pentru rute publice
    profile: default      # cheie configurabilă, fără secret
    policy: bearer required # valoare derivată pentru raport
  • MUST tipul de autentificare să fie reprezentat printr-un enum/union extensibil: None, Bearer, ApiKey, Basic, Custom;
  • MUST cerința de acces să fie separată de mecanism: Optional nu înseamnă automat „fără auth”, iar Required nu trebuie dedus din numele profilului;
  • MUST profilul să rămână configurabil și să fie verificat față de auth profiles la startup/runtime;
  • MUST executorul să raporteze separat contractul declarat de rută (route.auth.type, route.auth.requirement, route.auth.profile) și profilul efectiv aplicat (auth.profile, auth.mode, auth.token.state);
  • MUST NOT tokenul, headerul Authorization sau valoarea secretului să apară în HTML;
  • politica text anonymous allowed/bearer required este derivată pentru lizibilitate și nu este sursa de adevăr.

Acest model permite o rută nouă să fie mutată între medii prin configurație fără a pierde intenția semantică din raport. Un profil configurat greșit trebuie să fie vizibil ca nepotrivire între route.auth.* și auth.*, nu ascuns printr-un mesaj generic „anonymous”.

12. Cerințe non-funcționale

Determinism: seed, deadline și retry budget sunt logate.
Parallel safety: context și date scoped per test.
Security: secret masking înainte de reporting.
Diagnostics: status, headers safe, body safe, duration, attempts.
Reproducibility: config snapshot fără secrete.
Resilience: 429 și timeout testabile cu fake transport.
Extensibility: resource/validator noi fără modificarea engine-ului.
API/UI isolation: zero browser initialization în API core.
Performance: reutilizare HttpClient/handler; fără socket churn per pas.
Report integrity: un singur writer/flush sincronizat.
Reguli de securitateobligatorii
În sursa analizată există un token concret în src/main/resources/framework.properties. Pentru orice implementare nouă: revocare/rotire a tokenului, eliminarea lui din Git și injectare exclusivă din secret store/CI. Documentul nu reproduce valoarea.
  • masking pe nume de header și JSONPath;
  • body raw nu se scrie în log dacă content type sau contractul declară secret;
  • URL query params sensibili sunt redacționați;
  • stacktrace-ul nu include tokenul și nu publică dump-uri de environment;
  • report artifacts au retention și ACL definite.

Concluzie operațională

Pentru a recrea acest API ATF în .NET, trebuie reprodus comportamentul și contractul, nu structura Java: un motor generic citește scenarii configurabile, execută operații de service printr-un executor HTTP comun, aplică retry/polling controlat, validează răspunsul prin reguli declarative și publică totul într-un singur raport Extent dark, colapsabil și sigur.

Ordinea recomandată de implementare: 1) config/schema + secret handling → 2) Extent lifecycle → 3) request/response kernel → 4) validators/schema → 5) cleanup/captures → 6) Users smoke/negative → 7) Posts relationships/pagination → 8) contract tests și parallel hardening.
ATF API requirements baseline • document autonom • analiză locală a sursei Java ATF1 • Extent-only pentru ținta .NET

Regulă UI — barele Overview secondary

Titlurile ATF execution metadata (secondary) și ATF tag audit (secondary navigation metadata) trebuie să fie clar dominante față de textul descriptiv: 1.1rem, line-height 1.4, font-weight 550. Eticheta din dreapta rămâne secundară la .85rem. Barele rămân colapsate implicit și nu se modifică geometria tabelelor native.

Clarificare obligatorie — pașii API și validările sunt frați în fază

Modelul vizual trebuie să urmeze Extent: scenario → SETUP / TEST BODY / TEARDOWN → request HTTP + validation step(s). Validarea nu este copilul requestului și nu trebuie înconjurată de o subsecțiune artificială CONTRACT VALIDATION. Requestul deține doar dovada de transport, response details și JSON; fiecare pas Validate: ... este un card-soră, colapsat implicit, care deține un singur tabel agregat ASSERTION / EXPECTED / ACTUAL / RESULT.

NivelConținutInteracțiune
Phase shellSETUP, TEST BODY, TEARDOWNcolapsat implicit; doar container de navigație
HTTP requestmethod/path, trace, response JSON și request bodycolapsat implicit; evidence intern independent
Validation siblingValidate: contract și un tabel complet de aserțiunicolapsat implicit; se deschide independent de request
Testabilitate: testele structurale trebuie să verifice că TEST BODY.Children conține requestul și validările în ordinea execuției, că requestul nu are validări ca descendenți și că randarea finală păstrează aceleași carduri-soră.

Normă de prioritate — ierarhia request / validation

Normativ pentru implementare: dacă o formulare anterioară din acest document descrie validarea ca nod copil al requestului, se aplică această versiune: validările sunt carduri-soră ale requestului, direct sub faza SETUP, TEST BODY sau TEARDOWN. Requestul nu conține carduri Validate: ...; el conține doar evidence-ul transportului și payload-urile. Fiecare validare are tabelul agregat propriu și se deschide independent.

Normă finală — request + validation, tabel agregat

Această secțiune are prioritate față de formulările istorice care nu disting evidence-ul de verdict. Modelul verificat în raportul ATF este: sub aceeași fază, requestul HTTP deține trace-ul și payload-urile, iar validarea contractului este un card-soră asociat acelui response.

SCENARIO → SETUP / TEST BODY / TEARDOWN → (HTTP REQUEST → TECHNICAL TRACE + JSON) + (CONTRACT VALIDATION → ASSERTIONS · N). Regula: un ApiResponse = un tabel agregat. Răspunsurile HTTP diferite = noduri și tabele diferite.
